# MT7621A — WayangOS on a 4-thread MIPS router

Status: **proposal / roadmap**, 2026-10-03. Nothing here exists yet unless marked
`[x]`. Companion docs: [`DISTRIBUTION.md`](DISTRIBUTION.md) (how an image reaches a
client), [`UPDATE-DESIGN.md`](UPDATE-DESIGN.md) (the A/B + bundle format),
[`BUILDING.md`](BUILDING.md) (how an image is built today),
[`CHANNEL.md`](CHANNEL.md) (the update channel).

Goal: a client-class MT7621A router (2 cores / 4 threads, **512 MB RAM, 128 MB NAND**)
that runs wayang-fw + wayang-router, routes at line rate on a gigabit LAN/WAN, and
can be managed (locally or from the console on another box) — i.e. the same product
promise as the x86 editions, on a USD-40 board.

Status legend: `[ ]` open · `[~]` in progress · `[x]` done · `[?]` needs a decision
or a measurement before it can be scheduled.

---

## 0. The hardware, and the bar it is measured against

| | MT7621A (this port) | MikroTik hEX S / RB760iGS (the bar) |
|---|---|---|
| SoC | MediaTek MT7621A, 880 MHz, **2 cores / 4 threads** | **same** MT7621A |
| RAM | 512 MB (board-dependent) | 256 MB |
| Flash | 128 MB NAND | (vendor, small) |
| Datapath | kernel netfilter + switch, as we build it | RouterOS fasttrack + hardware NAT |
| Crypto | no Linux driver work done yet `[?]` | **IPsec hardware encryption ~470 Mbps** (MikroTik's own figure) |
| Software | wayang-fw + wayang-router + BusyBox | RouterOS |

Source for the bar: MikroTik's hEX S datasheet
(<https://cdn.mikrotik.com/web-assets/product_files/hEX__S_191220.pdf>) — "CPU
MT7621A, CPU nominal frequency 880 MHz, CPU core count 2, CPU threads 4, Size of RAM
256 MB, IPsec hardware encryption (~470 Mbps)". The point of the table is that the
*silicon is identical*: what separates the two devices is software (offload and
crypto), not the chip. Nothing in this document claims we match RouterOS until §4's
measurements say so.

Reference for the platform side: OpenWrt ships this SoC as the `ramips/mt7621`
target (e.g. <https://cdimage.debian.org/mirror/openwrt.org/releases/24.10.0/targets/ramips/mt7621/>),
which is where the useful kernel patches for this SoC live (see §2.1).

## 1. Where WayangOS is today (the port's starting line)

Verified facts, with the file that says so:

* **x86_64 only.** `scripts/build-kernel.sh:32-35` and `scripts/build-rootfs.sh:33-35`
  hard-error on any `ARCH` other than `x86_64|arm64`; the release pipeline names the
  ISO `…-installer-x86_64.iso` (`wayangos/scripts/ci-build.sh:28`) and fetches x86_64 artifacts only
  (`wayangos/scripts/build-remote.sh:77,79`); the meta JSON hardcodes `"arch":"x86_64"`
  (`wayangos/scripts/build-installer-iso.sh:169`). **Grep for `mips|mipsel|MT7621` across the whole
  repo: zero hits.**
* **arm64 is wired but pre-release** (M7): `ARCH=arm64` is accepted with
  `CROSS_COMPILE=aarch64-linux-gnu-`, the static `curl` is skipped there
  (`wayangos/scripts/build-rootfs.sh:123-124` is the precedent for a per-arch gap), and
  `build-arm64-image.sh` only assembles a directory tree — bootloader bring-up is
  explicitly best-effort. Its kernel fragments carry **no** dataplane options.
* **The rootfs is the initramfs.** BusyBox 1.37.0 + Dropbear + static curl + pinned
  static tools (nft, iproute2/tc, BIRD 2.19.2, wireguard-tools, radvd, dnsmasq,
  conntrackd, wayangi, wayang-fw, wayang-router, dcheck). No libc, no package
  manager, everything static musl (`scripts/build-rootfs.sh:1545-1597`).
* **Storage model is x86-shaped**: 512 MiB vfat ESP `WAYANGBOOT` + ext4 `WAYANGDATA`,
  GRUB with A/B slots and `grubenv` fallback state
  (`docs/UPDATE-DESIGN.md:14-52`). There is no NAND/UBI layout, no squashfs, no
  overlay anywhere in the repo.
* **Boot is GRUB/UEFI** (`installer/` writes it). An MT7621A board boots U-Boot from
  NAND — none of that machinery applies. This is the single biggest structural gap:
  the port is *not* only "add an arch to the build scripts".
* **The dataplane is nftables, and the fast path is switched off.** wayang-fw renders
  one `table inet wayang_fw` (`TABLE` at `wayang-fw/src/render.rs:25`, emitted at `wayang-fw/src/render.rs:1009`) with seven base chains
  (prerouting/mangle DoS, prerouting/raw notrack, input, forward, output, nat
  prerouting/dstnat, nat postrouting/srcnat). The kernel *capability* is compiled in
  — `CONFIG_NF_FLOW_TABLE=y`, `CONFIG_NF_FLOW_TABLE_INET=y`,
  `CONFIG_NFT_FLOW_OFFLOAD=y` at `configs/defconfig-intel:97-99` — but **no
  `flowtable` object and no `flow add @ft` statement is ever rendered**, so every
  packet of every flow walks the hook chain. See §3.1.
* **wayang-router does no firewalling by design** (`wayang-router/AGENTS.md:27-28`):
  it plans `ip`/`vconfig`/`brctl`/`wg`/`tc` steps, speaks BIRD's control socket, and
  never touches nftables.
* **The tools publish pinned per-arch assets**: `wayangos/scripts/build-wayang-fw.sh:19-23` /
  `wayangos/scripts/build-wayang-router.sh:19-23` download
  `wayang-{fw,router}-v…-x86_64-unknown-linux-musl` with a sha256 pin. A MIPS port
  needs those artifacts to exist first (a wayang-fw / wayang-router release per arch).
* **The web console is not in this image at all.** WayangOS bakes no webui; it bakes
  the three TUIs and starts HTTP APIs **only when `<conf>/api.args` exists**
  (`/etc/init.d/api`, "a default image listens on nothing").
* **Minimum spec today**: 72 MiB RAM (x86_64, `docs/MINIMUM-SPEC.md`) for the core
  system — the *base* OS is tiny; everything interesting is what we add on top.

## 2. Decisions this port forces

These are the five questions that must be answered before code, because they shape
every milestone in §4.

### 2.1 Kernel source: mainline mt7621, or OpenWrt's tree? `[?]`

* **Mainline** (`KERNEL_VERSION=7.2.7`, what the repo builds today): boots MT7621 via
  the upstream ralink/MT7621 device trees and `mtk_eth_soc` + `mt7530` DSA. **No
  hardware NAT/PPE offload** — that patch set lives downstream (OpenWrt). Software
  flowtable (§3.1) *is* available in mainline and is the Phase-1 lever.
* **OpenWrt's kernel tree as a "flavor"** (the way `KERNEL_FLAVOR=rt` selects the
  PREEMPT_RT tree today, `scripts/fetch-sources.sh:34-51`): carries the MT7621
  hardware-NAT patches. Cost: we stop being "mainline + our fragments", and the
  flavour needs its own fragment, its own rebuild cadence, and its own risk story.
* **Recommendation**: Phase 1 on **mainline + software flowtable** (measurable, no
  patch debt). Phase 2 evaluates the OpenWrt flavour *against §3.4's numbers*: if
  software flowtable already lands at line rate on a 1 GbE WAN, hardware PPE is
  optional work we can decline.

### 2.2 Boot chain: how does a U-Boot/NAND board get a WayangOS? `[?]`

Options, in ascending cost:

1. **Initramfs-in-NAND (closest to today)**: one image (kernel + initramfs) written
   to NAND, U-Boot loads it, system runs from RAM exactly as it does on x86. /data
   lives on a NAND partition (or in RAM, lost on reboot). Cheapest port; the update
   story becomes "write the image partition" (like a router firmware flash).
2. **squashfs root + overlay**: read-only root on NAND, writable overlay (or /data
   only), like OpenWrt. Better wear story, more build work (the rootfs pipeline
   produces a cpio today).
3. **Dual-image A/B in NAND** with a U-Boot environment flag, matching the *promise*
   of the x86 A/B model (`docs/UPDATE-DESIGN.md:59-70`, 3 failed boots → last good).

* **Recommendation**: (1) to boot, then (3) to ship — the A/B promise is the product's
  safety net and should not be silently dropped on this board. Boards whose U-Boot
  cannot be modified (most consumer routers) fall back to (1) + a documented
  manual-recovery procedure.

### 2.3 Storage and wear `[?]`

128 MB NAND must hold: image(s), config, history, logs. Today a confirmed box writes
`/data/var/wayang-{fw,router}/history.jsonl` (trimmed to 20000 records **once per
boot**), `/data/etc/*/candidate.toml`, logs to tmpfs (`syslogd -s 200 -b 2`), and the
web console's audit/telemetry if it runs here. Options: keep `/data` on NAND with a
hard trim + fsync discipline, or keep `/data` in RAM and snapshot only config to
NAND. **Recommendation**: config + wayangi token on NAND (small, rarely written),
history/logs on tmpfs with the existing trim, and a deliberate decision per file —
written up as a table in the port's own `docs/` before flashing client hardware.

### 2.4 Does the web console run on the box, or manage it from elsewhere? `[?]`

The console's real cost, measured/sourced from `wayang-webui` (not estimated):

| Cost | Fact |
|---|---|
| Binary | 7.4 MB static musl, assets embedded (~137 KB: app.css 71.3 KB, htmx 50 KB, app.js 15.3 KB) |
| Runtime | `tokio::runtime::Runtime::new()` with **no override → one worker per core**, i.e. all 4 threads of an MT7621A competing with forwarding (`wayang-webui/src/main.rs:97`) |
| Sign-in | argon2id `m=19 MiB, t=2, p=1` per attempt (`wayang-webui/src/auth.rs:47-56`) — fine, but not free on 880 MHz |
| Telemetry store | 24 h raw / 5-min rollups, `RAW_CAP 43200`, `MAX_SERIES 20000`, persisted as **daily JSONL under `<data_dir>/metrics/`** (`wayang-webui/src/telemetry/store.rs`) |
| Other files | `audit.jsonl` (4 MiB rotation, one generation), `alerts-active.json`, `alerts.jsonl`, `silences.json` (HISTORY 2000, MAX_FILE 4 MiB) |
| Poller | one task per box, default 15 s (per-device override) — each poll is an authenticated HTTPS GET to that box's API |
| Box-side API | `wayang-api` is **thread per connection**, `max_conns 32`, 1 MiB bodies; the fw read side spawns `nft list` per counter sample (throttled to 2 s) |

So on 512 MB it fits comfortably; on 4 threads at 880 MHz it is a *real* tax on the
forwarding cores unless it is capped. Two concrete asks if option B is chosen:
`[ ]` a config knob for the console's worker-thread count (today there is none), and
`[ ]` `data_dir` on tmpfs with only config snapshotted to NAND (§2.3) — and a clear
statement of what that loses (rollup history, resolved alerts, changes, audit log).

Remote management is already first-class: a device is `url` + `token` (or
`token_file`) with optional `ca`/`client_cert`/`client_key` for mTLS
(`src/config.rs`, `wayang-webui/src/upstream.rs:226-282`). The only loopback assumptions are the
default device URL and the lifecycle self-lockout guard
(`wayang-webui/src/web/pages/lifecycle.rs:610-628`) — which is exactly right when the console runs
off-box (it simply never applies), and must be reviewed if it runs on the box itself.

* **Option A (recommended for client fleets)**: the router runs only wayang-fw +
  wayang-router + their `api` with `--ro` (or `--rw` for the console's lifecycle
  pages), and the **console runs off-box** (the operator's machine, a VPS, or the
  existing x86 deployment) with the router as a `[[device]]` — remote management is
  already supported and is the shape the console was built for.
* **Option B**: bake the console into the MT7621A image (a new arch in
  `TARGETS`/asset feed, plus a console kernel fragment). Only if the product needs a
  standalone unit with no other management host.
* Either way: **measure first** (M4) — the console's RSS on the target is currently
  unmeasured `[?]`.

### 2.5 Arch naming for the channel and the build `[?]`

The channel is laid out as `<base>/<channel>/<arch>/manifest.json`
(`docs/CHANNEL.md`), with `x86_64` and `arm64` today; the bundle is
`wayang-<version>-<arch>.wup`. Proposal: **`mipsel`** — matching the Rust triple
`mipsel-unknown-linux-musl` and the kernel's `ARCH=mips`/`CROSS_COMPILE=mipsel-linux-…`,
with OpenWrt's `ramips/mt7621` (`mipsel_24kc`) as the ABI reference we must match for
any binary that talks to the base system. Decide the name once; it lands in the
channel paths, the asset names (`wayang-fw-v…-mipsel-unknown-linux-musl`) and the
installer's meta JSON.

### 2.6 What "full feature" means on this box `[?]`

| Feature | On MT7621A | Note |
|---|---|---|
| NAT/routing + policy rules | **yes** — the core product | needs the flowtable path (§3.1) for line rate |
| Port forwards, DoS/rate limits, SYN proxy | yes | SYN-proxied traffic stays in the slow path (see §3.2) |
| WireGuard | yes, CPU-bound | no crypto accel in Linux today `[?]`; measure |
| IPsec (ESP) | `[?]` | RouterOS claims ~470 Mbps via the SoC's engine; whether mainline exposes it is an open question |
| BGP/OSPF (BIRD 2) | small tables only | 4 threads; a full-table BGP session is a different product class |
| DHCP/DNS (dnsmasq), IPv6 RA (radvd) | yes | light |
| QoS: CAKE/HTB | **~150 Mbps class**, per public MT7621 reports | and **incompatible with offload** (§3.2) — a documented either/or |
| conntrackd state sync (HA) | technically yes, practically no | offloaded flows bypass conntrack; see §3.2 |
| WAF / L7 (Coraza, Go binary) | **no** | Go binary + CRS rule memory on 512 MB / 4 threads is the wrong product fit |
| Traffic logging (every packet) | sparingly | per-packet logging is what offload exists to avoid |

## 3. The performance plan (the part that decides whether this is worth doing)

### 3.1 Add a flowtable to wayang-fw's ruleset `[ ]`

This is the whole ballgame: it is the difference between "a Linux router on MIPS" and
"a router that routes at wire speed".

* Where: `wayang-fw/src/render.rs`, the function that assembles
  `table inet wayang_fw` (base chains at `wayang-fw/src/render.rs:484,485,651,696,732/768,882,958`;
  table emitted at `wayang-fw/src/render.rs:1009` (`TABLE` at `:25`)). New output: a `flowtable` object
  (`flowtable ft { hook ingress priority filter; devices = { … }; }` — the device list
  comes from the same config that lists interfaces/zones) plus a `flow add @ft`
  statement in the **forward** chain, placed after the rules that must still see the
  first packet and before the per-packet work.
* Config: a new `system.offload` (bool, default off until measured) so nothing changes
  for existing boxes without an explicit decision; the HUD/status should show whether
  the flows are actually in the table (`nft list flowtable`).
* Kernel: already enabled for x86 (`configs/defconfig-intel:97-99`); the new
  `configs/defconfig-mt7621` must carry the same three symbols.
* Acceptance: `[ ]` a lab test that a flow appears in the flowtable
  (`nft list flowtable inet wayang_fw`) and that a long-lived TCP flow stops
  incrementing the forward chain's counters — proving the fast path is real, not
  configured.

### 3.2 The rules that must not silently defeat offload `[ ]`

These are the design constraints the port has to state out loud, because each one is
a *product decision*, not a bug:

* **QoS (§2.6)**: a qdisc (CAKE/HTB) is bypassed by offloaded flows. Offload and SQM
  are an either/or; the config should refuse (or warn hard) when both are enabled.
* **conntrackd state sync**: offloaded flows are not in conntrack, so an HA failover
  loses them. `[ha] state_sync` + `system.offload` must warn the same way.
* **SYN proxy**: `notrack` (render.rs:485) and `synproxy` (render.rs:603-611) mean
  those packets never become conntrack entries and therefore cannot be offloaded —
  DoS-protected services ride the slow path by design. Fine, but it must be said.
* **Policy NAT via `ct mark`** (render.rs:820-821): applied when the flow is created;
  offload then carries it. Verify in the lab that hairpin/DNAT + offload compose
  (a wrong NAT tuple in an offloaded flow is invisible until traffic breaks).
* **Logging**: implicit-deny logs (`system.log_dropped`, default **true**) and DoS
  logs still fire on the first packet of a flow; per-packet traffic logging does not.
  That is the correct behaviour and should be documented for operators.
* **The WAF (NFQUEUE/TPROXY) and offload are mutually exclusive** for the traffic
  they inspect.
* **IPv6**: the `inet` flowtable covers v6, but hardware offload on MT7621
  (OpenWrt's PPE patches) is IPv4-only — an asymmetry to document if §2.1 phase 2
  happens.

### 3.3 CPU, IRQ and interface tuning `[ ]`

* CPU governor to `performance` (`CONFIG_CPU_FREQ` governors exist in the x86
  fragments; the MT7621 fragment needs its own — the current x86 one is ACPI-shaped).
* Pin the ethernet IRQ(s) away from the core doing the conntrack work `[?]` — verify
  the SoC's IRQ layout first; `?` until measured.
* GRO/TSO/scatter-gather on by default; verify `mtk_eth_soc`'s offload features on
  the board, and that nothing (bridging, VLAN, tc) disables them.
* MTU/PPPoE: PPPoE on this SoC is CPU-heavy and does not offload; a client on PPPoE
  must be told what to expect (§3.4).

### 3.4 What we will measure, and how `[ ]`

No number in this document is a promise until this table is filled in on real
hardware. The lab is: two x86 boxes running `iperf3`, the MT7621A in the middle, the
`wayang-fw` ruleset from the client's own config, counters read with `nft -a list
ruleset` and `conntrack -C`, CPU read per core.

| Scenario | Metric | Target to meet (to be proven, not assumed) |
|---|---|---|
| IPv4 routed/NAT, 1 TCP stream | throughput | line rate (940+ Mbps) |
| IPv4 routed/NAT, 1000 streams | throughput | line rate, flat CPU per core |
| 64-byte UDP, routed/NAT | packets/s | the SoC's ceiling (measure first: pps is the honest metric) |
| Offload on vs off | CPU per Gbit | a large, visible drop; and the flow counters in §3.1 |
| Same, with `system.log_dropped = true` | throughput | unchanged (first-packet logging only) |
| PPPoE WAN | throughput | documented expectation, whatever it is |
| WireGuard | throughput | documented; no crypto accel claim |
| CAKE 100 Mbps shaping | throughput/CPU | documented; and the either/or with offload |
| Console polling the box (option A) | throughput impact | measurable but small at 15 s; measure with 60 s too |

Every row becomes a line in this doc when the lab runs. `wayangos/docs/ROUTER-TODO.md`
already lists "a flowtable throughput test" as an unchecked item — this is that item,
with the acceptance shape it needs.

## 4. Milestones

Each milestone is independently shippable and has an observable acceptance test.

### M0 — a MIPS kernel that boots and prints `[ ]`
* `scripts/build-kernel.sh` / `build-rootfs.sh`: add the arch to the allowlist
  (`mipsel`, `CROSS_COMPILE=mipsel-linux-musl-` or the OpenWrt SDK toolchain),
  keeping the existing "hard error otherwise" behaviour.
* New `configs/defconfig-mt7621` (fragment on top of a base), carrying at minimum:
  the SoC/DTB support, `mtk_eth_soc`, `mt7530` switch, `NF_TABLES` + `NF_FLOW_TABLE`
  + `NFT_FLOW_OFFLOAD`, `WIREGUARD`, `NF_CONNTRACK`, the tc/qdisc set the router
  needs, `CPU_FREQ` governors, watchdog, and no WLAN-for-the-sake-of-it.
* Acceptance: a board boots to a BusyBox prompt on the serial console from a
  U-Boot-loaded image; `uname -a` says what we expect; the switch ports link.

### M1 — the rootfs builds for MIPS `[ ]`
* Static MIPS builds of every baked tool: BusyBox, Dropbear, nft/iproute2,
  BIRD 2, wireguard-tools, radvd, dnsmasq, conntrackd (the `-x86_64-only` gap for
  `curl` has a precedent: warn and skip, `wayangos/scripts/build-rootfs.sh:123-124`).
* Acceptance: `file` says "statically linked, MIPS" for each (the existing scripts
  already assert this for C tools); the image is within the NAND budget; it boots,
  gets DHCP, accepts SSH, pings.

### M2 — flash layout, /data, reboot survival `[ ]`
* The NAND partition plan (§2.2/§2.3), `/data` persistence, the once-per-boot trims,
  and a documented recovery procedure for a bricked image.
* Acceptance: a written config survives a reboot; a power-cut during boot still
  boots; the recovery path is exercised once, by hand.

### M3 — the tools on the box `[ ]`
* Publish `mipsel-unknown-linux-musl` artifacts for wayang-fw / wayang-router (the
  Rust side: tier-3 target → nightly + `-Z build-std`, vendored deps, and the C
  cross-compiler that `ring`/rustls needs — see Risks).
* `build-wayang-fw.sh` / `build-wayang-router.sh`: add the arch with a sha256 pin;
  the boot path (lookup `/data/bin` then `/usr/bin`, confirmed-ruleset-only boot)
  stays as it is.
* Acceptance: `wayang-fw` applies a real ruleset on the board, `wayang-router`
  brings up a LAN/WAN pair, and both survive a reboot.

### M4 — offload, and the measurement matrix `[ ]`
* §3.1 + §3.2 + §3.3 implemented, and §3.4's table filled with real numbers.
* Acceptance: the flowtable test passes, and the two headline rows (line-rate TCP;
  CPU per Gbit with offload on/off) meet the target or the result is written down as
  the product's honest limit.

### M5 — updates on this board `[ ]`
* The A/B model re-cut for U-Boot/NAND (or the single-image + manual-recovery model,
  if the board's bootloader cannot be changed), a signed bundle for the arch, and the
  3-failed-boots fallback.
* Acceptance: an update from image A to B, a forced failure (corrupt image) rolling
  back, and `wayang update --check` seeing the new version over the channel.

### M6 — ship it to a client `[ ]`
* Per `DISTRIBUTION.md`: channel directory for the arch, the provisioning bundle, the
  support matrix entry, and the one-page runbook.
* Acceptance: a *fresh* board, out of the box, becomes a managed WayangOS router by
  following only the runbook — with no step that requires the maintainer.

## 5. Risks and open questions (ranked by how much they could sink the port)

1. **Hardware offload may be needed for the headline claim, and it lives
   downstream.** Mainline has no MT7621 PPE/flow-offload; OpenWrt's patches do. If
   software flowtable on this SoC lands well short of line rate, §2.1's phase 2
   becomes mandatory — and with it a vendor-kernel flavour. `[?]` until §3.4 runs.
2. **Rust tier-3 MIPS.** `mipsel-unknown-linux-musl` exists in `rustc --print
   target-list` but has **no prebuilt std** (checked on the build machine,
   rustc 1.98.1), so the tools need nightly + `-Z build-std`, a vendored dependency
   set, and a C cross-toolchain for `ring`/rustls. Pin the nightly; a floating
   toolchain will break client builds at the worst time.
3. **NAND wear.** History/metrics/log writes on a 128 MB NAND must be bounded by
   design (tmpfs + trim), or a box dies in the field. `docs/ROUTER-TODO.md`'s
   retention work is a prerequisite, not a nicety.
4. **U-Boot variance across boards.** Every board vendor ships a different U-Boot
   configuration (and some cannot be replaced). The support matrix must say what is
   supported, what is tested, and what is best-effort — and M2's recovery procedure
   must be per-board.
5. **1 core is not 4 threads.** Single-flow throughput on an 880 MHz in-order MIPS is
   core-bound; conntrack, nft, BIRD and the console all want a core. The measurement
   matrix must include a "busy box" scenario (BGP session + console poll + offload),
   not just an idle router.
6. **Crypto.** RouterOS's ~470 Mbps IPsec uses the SoC's engine through a vendor
   driver. Whether mainline exposes it (and whether it is worth a flavour) is unknown
   `[?]`. Do not quote an IPsec number for WayangOS until it is measured.
7. **The console's RSS is unmeasured on this class of box** `[?]`, and §2.4's option B
   (bake it in) makes that number load-bearing. Its tokio runtime takes one worker per
   core by default (`wayang-webui/src/main.rs:97`) — on a 4-thread router that is a scheduling
   decision made by a library, not by us; capping it is part of M4 if the console runs
   on the board.

## 6. Non-goals (for the first MT7621A release)

* **No hardware-offload promise** in phase 1 (§2.1); no vendor-kernel flavour until
  §3.4 justifies it.
* **No WAF/L7** (the Go binary + CRS is the wrong fit for 512 MB / 4 threads).
* **No eBPF/XDP**: deliberately off in this project
  (`configs/README.md:57-61`); the fast path here is netfilter's flowtable, not BPF.
* **Not a full-table BGP router.** Small peerings only; a full IPv4 table is a
  different hardware class.
* **Not a replacement for the x86 editions.** MT7621A is a new flavor: its own
  fragment, its own channel directory, its own support matrix — the x86 images,
  installer and update path stay untouched.
