# Product API — one API per tool (wayang · wayang-fw · wayang-router)

Status: **design** (2026-09-30); **P0 and P1 implemented for `wayang-router` and
`wayang-fw` on 2026-10-03** (see [PRODUCT-API-REFERENCE.md](PRODUCT-API-REFERENCE.md)).
The shared crate `wayang-api` (scopes, rate limit, TLS/mTLS, SSE events — the P2
transport) exists and the **`wayang` CLI's API is built on it** (update, slot
actions, reset, Edge bundle, SSH keys, net; `/etc/init.d/api` starts it only when
`api.args` exists). P3 (OpenAPI, the wayangi client) is still design. Goal: each console tool can be driven by an
**API** (not only the CLI/HUD), so an orchestrator — or wayangi — can read and
change a box without SSH-ing in and parsing TUI output.

This is the `wayang-router` roadmap §v1.0 item ("a local HTTPS API, the same
operations as the CLI, plan/commit/confirm, with tokens"), generalised to all
three tools.

## 1. Model

Every tool grows an **`api` subcommand**: a small local HTTP(S) server that
exposes the tool's existing operations as JSON.

```
wayang-router api [--listen 127.0.0.1:8631] [--token-file /data/etc/router/api-token] [--tls ...]
wayang-fw     api [--listen 127.0.0.1:8632] [--token-file /data/etc/fw/api-token]
wayang        api [--listen 127.0.0.1:8630] [--token-file /data/etc/wayangi/api-token]
```

Same binary, same `check/plan/commit` engine underneath — the API is a thin
transport over the code paths the CLI already uses (no second implementation of
the logic). A Read-only mode (`--ro`) disables every mutating route.

On WayangOS the server is started by an init script (`/etc/init.d/<tool>-api`,
generated like the others) **only when enabled** in config (`[api] enabled =
true`), so a default image listens on nothing.

## 2. Common endpoints (all three)

| method | path | does |
|---|---|---|
| GET | `/v1/health` | liveness + version + feature caps (no auth) |
| GET | `/v1/status` | the tool's `status` as JSON (engine, backend, active rev, drift) |
| GET | `/v1/config` | the active (or `?rev=N`) config as TOML/JSON |
| GET | `/v1/candidate` | the current candidate |
| PUT | `/v1/candidate` | write the candidate (validated; 422 with the field errors) |
| POST | `/v1/check` | validate the candidate (or a posted body) |
| POST | `/v1/plan` | the plan/diff the next commit would run (dry-run) |
| POST | `/v1/commit` | apply the candidate; `?confirm=60` arms commit-confirm |
| POST | `/v1/confirm` | keep a pending commit |
| POST | `/v1/rollback` | undo the pending commit |
| GET | `/v1/history` | revisions; `/v1/history/{n}` |
| GET | `/v1/events` | audit/event stream (SSE) — who changed what, when |

Semantics mirror the CLI exactly: **staging ≠ committing**, commit-confirm is
preserved (a bad change rolls back), and the same `caps` refusals apply (returned
as `409 conflict` with a plain-language reason).

## 3. Tool-specific endpoints

* **wayang-router** (read): `/v1/wan` (uplinks + health + which owns the default),
  `/v1/routes`, `/v1/wg` (tunnels/peers/handshakes), `/v1/bgp`, `/v1/dhcp`,
  `/v1/qos`. (write: the common config routes.)
* **wayang-fw** (read): `/v1/policies`, `/v1/nat`, `/v1/drops`, `/v1/logs`,
  `/v1/stats` (per-policy hits), `/v1/objects`.
* **wayang** (WayangOS): `/v1/status`, `/v1/update/check`, `POST /v1/update`
  (+`/confirm`), `POST /v1/reset`, `/v1/edgerouter/status`,
  `POST /v1/edgerouter/apply`, `/v1/net`, `/v1/wifi`, `/v1/ssh-keys`.

## 4. Auth & transport

* **Bearer token** from a file (`/data/etc/<tool>/api-token`, mode 0600,
  generated by `<tool> api --gen-token`). `Authorization: Bearer <token>`.
  Constant-time compare. Optional `Authorization` **mTLS** (client cert) for
  fleet use.
* **Bind loopback by default** (`127.0.0.1` / `[::1]`). Any other bind is an
  explicit opt-in (`--listen`) and is **never** allowed on a WAN zone by
  default; the box's firewall (wayang-fw) should only expose it on a management
  VLAN. Document the pairing.
* **HTTPS**: optional; self-signed or an operator cert. Plain HTTP is allowed
  only on loopback. No TLS 1.x<2 if HTTPS.
* Per-client token scopes (`ro` / `rw` / `admin`) and a simple rate limit.

## 5. Safety

* Mutating routes are **idempotent** with an `Idempotency-Key` header.
* Commit-confirm is mandatory unless the token has `admin` **and** the request
  sends `?confirm=0` explicitly (still recorded in the audit log).
* Every mutation is audited (`actor`, token id, source IP, path, result) to
  `/data/var/<tool>/api-audit.jsonl` and exposed via `/v1/events`.
* The API never bypasses `check`: a candidate that fails validation is refused
  with the same messages the HUD/CLI show.

## 6. Response shape

```json
{ "ok": true, "data": { … }, "rev": 7, "pending": null }
{ "ok": false, "error": { "code": "validation", "message": "…", "fields": {…} } }
```
HTTP codes: 200 ok · 201 created · 400 bad request · 401/403 auth · 404 · 409
conflict (caps refusal / drift) · 422 validation · 423 locked (another commit
pending) · 500.

## 7. Shared code

The transport/auth/audit layer is identical across the three → put it in a
shared crate (**`wayang-api`**, sibling of `wayang-tui`): request routing,
token auth, the JSON envelope, idempotency, audit, rate limit. Each tool only
implements its endpoints by calling its own existing functions. (This is the
same "one implementation, three clients" principle as `wayang-tui`.)

## 8. wayangi / orchestrator integration

This is how an orchestrator (or wayangi) drives an Edge box **without an
agent**: the bundle/API client calls `PUT /v1/candidate` + `POST /v1/commit`
(or `POST /v1/edgerouter/apply`). It also lets a future dashboard show live
router/fw state instead of only the static bundle.

## 9. Phases

* **P0 — read-only.** `api` subcommand, loopback, token, `/v1/health`,
  `/v1/status`, and the per-tool read endpoints. No mutation. (Lets a dashboard
  poll state.)
* **P1 — config lifecycle.** `/v1/config|candidate|check|plan|commit|confirm|
  rollback|history` with commit-confirm + audit. The full CLI parity.
* **P2 — tool actions + transport.** `wayang` update/reset/edgerouter apply;
  optional HTTPS + mTLS; scopes + rate limit; SSE `/v1/events`.
* **P3 — orchestration.** wayangi consumes the API; OpenAPI spec committed;
  a generated client for wayangi.

## 10. Open questions

1. Port numbering + a single front proxy vs one port per tool.
2. Token issuance/rotation: per-box manual vs fleet-distributed via the OS
   update channel.
3. mTLS from day one, or bearer token first?
4. OpenAPI as the source of truth (hand-written vs generated from the handlers).
5. Should the `api` server be a separate long-running service (like the
   monitors) or spawned per request? (Leaning: a supervised daemon, started by
   init only when `[api] enabled = true`.)
