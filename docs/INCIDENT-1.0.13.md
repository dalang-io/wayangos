# Incident: WayangOS 1.0.13 locks up the test device (2026-09-26)

Status: **open**. 1.0.13 is pulled from the update channel; the device is back
on 1.0.12. Read this before touching the release or the device again.

## Symptom

Test device `root@163.128.55.3` booted 1.0.13 (slot B) after `wayang update` +
reboot. The console **reaches the shell prompt**, then **the keyboard does
nothing** and the box is **unreachable** (SSH times out, no ping). It stays
like that; no reboot, no recovery by itself (attempts are only counted by GRUB
on the next boot).

## Device facts

| | |
|---|---|
| CPU | Intel Core i3-7100 (Kaby Lake), i915 console (fbcon, 1440×900) |
| Keyboard | SEMICO USB keyboard, **usb 1-8** on xHCI `0000:00:14.0` |
| Uplink `eth1` | **CoreChip SR9700 USB Ethernet** (`sr9700`), **usb 1-5**, same xHCI; DHCP, public `163.128.55.3/32`, gw `163.128.55.254` |
| Other NICs | `eth0` e1000e (onboard, cable present), `wlan0` iwlwifi (down) |
| `/data/etc/network` | `primary=eth1`, `MODE=dhcp` |
| `/data/bin` | `wayang-fw` 0.2.2, `wayang-router` 0.1.0 (no config committed for either) |

**Keyboard and uplink are both USB on the same controller, and both died
together.** The leading hypothesis is a USB/xHCI stall (or a hard CPU lockup),
not a console/tty problem.

## What changed 1.0.12 → 1.0.13

Commits `5ca5bdc`, `af35255`, `67b8d86` (tag `v1.0.13`):

1. **Kernel** (`configs/defconfig-intel`, router block). Resolved `.config`
   diff = only these, all `=y`: BONDING, BRIDGE (+IGMP_SNOOPING,
   VLAN_FILTERING), STP, LLC, VLAN_8021Q, DUMMY, VETH, MACVLAN, TUN, WIREGUARD
   (+CRYPTO_LIB_CHACHA/POLY1305/CURVE25519 incl. `_ARCH` x86 asm), NET_UDP_TUNNEL,
   NET_IPGRE(+DEMUX), NET_IPIP, IPV6_MULTIPLE_TABLES, INET_ESP, XFRM_INTERFACE,
   IFB, NET_SCH_{HTB,FQ_CODEL,CAKE,INGRESS}, NET_CLS_{U32,FW}, NET_ACT_{POLICE,MIRRED},
   NET_REDIRECT. Built-ins create `bond0`, `dummy0`, `ifb0/1`, `gre0`,
   `gretap0`, `erspan0`, `tunl0` at boot.
2. **rootfs** (`scripts/build-rootfs.sh`): rcS sets `nf_conntrack_acct=1`;
   `/etc/init.d/network start` first calls `/etc/init.d/router owns` (false
   here: no `/data/etc/router/config.toml`); new `/etc/init.d/router`;
   `/etc/udhcpc.script` skips resolv.conf when it starts with
   `# generated by wayang-router`.
3. **`wayang` binary**: new console HUD (not started at boot; tty1 runs
   `/bin/sh -l`).

## Ruled out

- **Corrupt staging**: `/boot/B/{vmlinuz,initramfs.img}` on the ESP match the
  release manifest sha256 (`19bc3ad5…`, `1d0c3424…`). The initramfs is 6.4 MB
  vs 21.9 MB for A only because of compression.
- **Broken artifact**: the released bundle boots in QEMU/KVM with the device's
  cmdline (`loglevel=3 wayang.data=LABEL=WAYANGDATA wayang.slot=B`), NVMe
  `/data` holding the same `/data/bin`, `-vga std`, xHCI + `usb-kbd`: keys
  typed on tty1 work (`touch /data/kbd` via QEMU `sendkey`), SSH works — with a
  PCI e1000 **and** with a USB NIC (`usb-net`) on the same xHCI. Script:
  "Reproduce in QEMU" below.
- A HUD grabbing tty1: nothing autostarts on tty1.

Not ruled out: anything specific to this hardware (sr9700, xHCI on Kaby Lake,
i915), a kernel option above misbehaving on real hardware, or a userspace
change that only triggers with the real NICs (e.g. udhcpc on the USB NIC).

## How to find it (needs the device + someone at the screen)

Slot A (1.0.12) is **good** and GRUB boots it by default, so trying slot B is
safe: pick "slot B" in the GRUB menu (3 s timeout), and power-cycle to get
back. **After every manual pick**, see "Recovery" (updater bug).

1. **Is the kernel alive?** On the frozen screen press Caps Lock (LED toggles
   = kernel handles USB input interrupts) and Ctrl-Alt-Del (`inittab` →
   reboot). No reaction at all → hard lockup or xHCI stall.
2. **Remove USB from the equation**: unplug the sr9700 adapter, put the uplink
   cable in `eth0` (e1000e), boot B. If the keyboard now works, the trigger is
   the USB NIC path (sr9700 + something new in 1.0.13).
3. **Get a log out**: the net and keyboard die, so keep one on disk. Build a
   debug image (see below) whose rcS starts
   `( while :; do dmesg > /data/dmesg.boot; cat /proc/interrupts > /data/irq.boot; sync; sleep 1; done ) &`
   right after `/data` is mounted; boot B, wait for the freeze, power-cycle to
   A, read `/data/dmesg.boot`. Also drop `loglevel=3` (press `e` in GRUB) to
   see kernel messages on screen.
4. **Bisect kernel vs rootfs**: stage mixed bundles with
   `wayang update --from X.wup` (signed with the release key on the build box):
   1.0.13 kernel + 1.0.12 initramfs, and the reverse. If the kernel is to
   blame, halve the router option block in `configs/defconfig-intel` (first
   suspects: WIREGUARD's arch crypto, BONDING/DUMMY/IFB/tunnel devices created
   at boot, NET_SCH_* built-ins).

### Building a test bundle

On `root@10.0.0.251` in a `/tmp` build dir (never `/root/wayangos-build`), as
in docs of `dalang-io/wayang-router` → `docs/TESTING.md`:
`BUILD=$L KDIR=$L/linux-7.2.7 bash scripts/build-kernel.sh defconfig-intel`,
`BUILD_DIR=$L bash scripts/build-rootfs.sh`, then `scripts/build-bundle.sh`
with the release key to get a `.wup`. Copy it to the device with
`ssh root@163.128.55.3 'cat > /data/x.wup' < x.wup` (no sftp-server on the
device; large uploads can drop — verify sha256).

### Reproduce in QEMU

```sh
# on root@10.0.0.251; bundle from the GitHub release v1.0.13 (tar: vmlinuz, initramfs.img, manifest.json[.sig])
cd /tmp/rel1013 && tar xf ../wayang-1.0.13-x86_64.wup
truncate -s 64M d.img && mkfs.ext4 -q -F -L WAYANGDATA d.img   # add bin/, etc/ssh/authorized_keys
qemu-system-x86_64 -enable-kvm -m 1024 -smp 2 -kernel vmlinuz -initrd initramfs.img \
  -append "loglevel=3 wayang.data=LABEL=WAYANGDATA wayang.slot=B" \
  -drive file=d.img,if=none,id=d0,format=raw -device nvme,serial=x,drive=d0 \
  -device qemu-xhci -device usb-kbd -vga std -display none \
  -netdev user,id=n,hostfwd=tcp:127.0.0.1:2299-:22 -device usb-net,netdev=n \
  -monitor unix:mon.sock,server,nowait
# keys: echo "sendkey t" | socat - UNIX-CONNECT:mon.sock ; screen: "screendump s.ppm"
```

## Recovery (and the updater bug it exposed)

- To get back to 1.0.12: pick slot A in the GRUB menu, or power-cycle; GRUB
  falls back to `wayang_good` after 3 failed attempts **only if good is A**.
- **Bug (fixed on master `6db57a3`, not yet released)**: `wayang mark-ok`
  marked the slot GRUB *planned* (`wayang_slot`) instead of the one that booted
  (`wayang.slot=` on `/proc/cmdline`). After a manual pick of A, rcS marked **B
  (broken) as good** → next boot B again, and the fallback also B = boot loop.
  `stage` and `status` had the same assumption. Until a release carries the
  fix, after booting A by hand run on the device:
  ```sh
  grep -o 'wayang.slot=[AB]' /proc/cmdline    # confirm A
  wayang update --rollback && wayang mark-ok  # -> active A, boot next A, good A
  wayang status
  ```

## 1.0.14 — prepared, not published (master `ee1f8dc`)

Prepared in place of 1.0.13. Contains:

- the updater fix `6db57a3` (mark-ok/stage/status use the booted slot);
- an **opt-in diagnostics mode**: `wayang.debug` on the kernel cmdline makes rcS
  write `dmesg`, `/proc/interrupts` and `/proc/loadavg` to `/data/debug/` every
  second, so a freeze can be read back after a power-cycle. Off by default.
- the router kernel block is **unchanged from 1.0.13** (still the prime
  suspect). A "safe" variant with that block reverted can be built on request.

Verified: builds (`wayangos-1.0.14-…iso`, `wayang-1.0.14-x86_64.wup`) and boots
in QEMU/KVM with xHCI + `usb-kbd` + `usb-net` + NVMe `/data`: version 1.0.14,
USB keyboard present, SSH reachable. **Not tagged or published.**
